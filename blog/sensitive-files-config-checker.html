Sensitive Files & Config Checker: Finding Exposed .env, .git, and Backups Before Attackers Do

By Artem Kysylov

A missing Content-Security-Policy is a weakness. An exposed .env file is the keys to the building. In bug bounty programs and real audits alike, the single highest-impact findings almost never come from clever exploitation — they come from someone leaving a backup, a .git folder, or a config dump sitting in a directory the webserver happily serves to anyone who asks. No authentication to bypass, no payload to craft, just a GET request to a path a deploy script forgot to clean up.

That's the gap Sensitive Files & Config Checker (config_checker.py) closes. It's a CLI tool that walks a target host through a list of known-dangerous paths — version control internals, environment files, database dumps, archive backups — and confirms, by content rather than by status code, whether each one is actually sitting there exposed. Below is a breakdown of how it avoids the false positives that make naive scanners useless against modern web apps, followed by the terminal output and the hardening steps that close every finding it raises.

Why Naive Status Checks Fail on Modern Apps

The obvious approach — request each path, flag anything that returns 200 OK — worked fine against the static sites and classic LAMP stacks of a decade ago. It falls apart against a modern single-page app or a framework with a custom router, because those apps frequently don't have a real 404 at all. A React or Vue router catches every unmatched path client-side and serves the same index.html shell with a 200; a custom Express or Django error handler renders a friendly "Page Not Found" page, also with a 200. Request /.env on a site like that and you get a 200 whether or not the file exists — the status code alone tells you nothing.

A scanner that trusts status codes blindly either floods a report with false positives on every SPA it touches, or gets tuned down until it misses real findings too. config_checker.py avoids both failure modes by never trusting a single response in isolation — every hit gets compared against a calibration baseline and verified against the actual bytes of the file before it's reported.

"A 200 OK on /.env means nothing by itself. The question that matters isn't 'did the server respond' — it's 'does this response contain a key=value pair, or does it contain the same 400 bytes of fallback HTML every other dead path on this host returns?'"

Architecture & Code Breakdown

config_checker.py is built around three cooperating pieces: a calibration step that learns what "nothing here" looks like on the target before scanning anything, a streaming fetch layer that confirms a file's identity from its first bytes instead of downloading it in full, and a scan loop that turns a raw response into a severity-ranked finding. Here's how each one works.

1. Soft 404 Baseline Calibration

Before checking a single sensitive path, the scanner requests something that is guaranteed not to exist: a randomized, nonsense route. Whatever comes back — status code, body size, content type — becomes the baseline every later response gets compared against, instead of being judged against the HTTP spec in a vacuum.

config_checker.py Python 
# A guaranteed-absent, randomized path — not a real resource, not a
# reserved route — so whatever comes back defines what "nothing here"
# looks like on this specific host.
PROBE_PATH = "/non-existent-audit-probe-948271"


def _get_soft_404_baseline(self, base_url: str) -> tuple[int, int]:
    """Probe a path that cannot exist and record its status + size.
    SPAs and custom routers rarely return a real 404 — they serve
    the same index.html, or a friendly "Not Found" page, with a
    200 OK. That turns a naive `if status == 200` check into a
    false positive on every path this scanner tries. Calibrating
    first makes every later comparison relative to this host,
    not to the HTTP spec."""
    probe_url = urljoin(base_url, PROBE_PATH)
    try:
        resp = self.session.get(probe_url, timeout=self.timeout)
        return resp.status_code, len(resp.content)
    except requests.RequestException:
        # Calibration failing is itself a signal — treat every later
        # hit as suspicious rather than silently trusting a bare 200.
        return 0, 0

Running this once per target, before the real scan starts, is what lets a single host with a custom 404 page and a host with a textbook Apache 404 get scanned by the exact same logic without either one producing noise.

2. Memory-Safe Streaming & Magic Byte Signatures

Confirming a path is real still isn't enough — a 200 that isn't the baseline could still be an unrelated page. The only reliable proof is the content itself: a ZIP archive starts with the bytes PK\x03\x04 no matter what it's named, a Git config file starts with [core], a SQL dump starts with CREATE TABLE. SENSITIVE_PATHS pairs each target path with the signature that proves a hit is genuine, and _fetch_snippet reads only enough bytes to check it.

config_checker.py Python 
# Each entry pairs a known-sensitive path with the byte signature
# that proves a response is the real file, not a redirect or an
# unrelated page that happens to share the status code.
SENSITIVE_PATHS = {
    "/.git/config":        {"category": "vcs",     "signature": b"[core]"},
    "/.env":               {"category": "secrets", "signature": None},
    "/backup.zip":         {"category": "backup",  "signature": b"PK\x03\x04"},
    "/dump.sql":           {"category": "backup",  "signature": b"CREATE TABLE"},
    "/wp-config.php.bak": {"category": "config",  "signature": b"DB_PASSWORD"},
}

SNIPPET_BYTES = 512


def _fetch_snippet(self, url: str) -> tuple[requests.Response, bytes]:
    # stream=True holds the body back until we actually ask for it —
    # a hit on /dump.sql or /backup.zip can be multiple gigabytes,
    # and confirming it only needs the first 512 bytes.
    resp = self.session.get(url, timeout=self.timeout, stream=True)
    snippet = next(resp.iter_content(chunk_size=SNIPPET_BYTES), b"")
    # Closing here releases the connection without ever pulling the
    # rest of the body — it's the socket we free, not the archive.
    resp.close()
    return resp, snippet

This is the difference between confirming a file and downloading it. A 40 GB backup.zip left in a public directory is exactly the kind of finding this tool exists to catch, and iter_content(chunk_size=512) means catching it costs 512 bytes of memory and one read, not 40 GB of bandwidth and a timeout.

3. Context-Aware Severity & 403 Detection

scan is where the baseline and the signatures come together. Every response gets filtered against both before it's allowed to become a finding — and a 403 gets treated as a finding in its own right, because a server can only refuse to serve a file it first confirmed exists.

config_checker.py Python 
def scan(self, base_url: str) -> None:
    baseline_status, baseline_size = self._get_soft_404_baseline(base_url)

    for path, meta in SENSITIVE_PATHS.items():
        url = urljoin(base_url, path)
        try:
            resp, snippet = self._fetch_snippet(url)
        except requests.RequestException:
            continue

        if resp.status_code == 403:
            # Blocked, not absent — the webserver had to resolve the path
            # to a real file on disk before it could refuse to serve it.
            # Worth logging even though nothing was actually read.
            self._log(url, "INFO", "HTTP 403 Forbidden — file exists on disk, access blocked")
            continue

        if resp.status_code != 200:
            continue

        content_type = resp.headers.get("content-type", "").split(";")[0]
        if content_type == "text/html":
            # A target like /.git/config should never legitimately render
            # as a webpage — this is almost always the same SPA fallback
            # or error page the baseline probe already returned.
            continue

        size_delta = abs(len(resp.content) - baseline_size)
        if resp.status_code == baseline_status and size_delta < 32:
            # Same status *and* roughly the same body size as "nothing
            # here" — this is the soft-404 the baseline exists to catch.
            continue

        signature = meta["signature"]
        if signature and signature not in snippet:
            continue

        severity = "CRITICAL" if meta["category"] in ("vcs", "secrets") else "HIGH"
        self._log(url, severity, f"Exposed {meta['category']} file confirmed")

Note the ordering: text/html gets filtered before the size comparison, because an HTML error page can coincidentally land within 32 bytes of the baseline on some hosts and within hundreds on others — content type is the cheaper, more reliable signal to check first. Only after a response survives both filters does it even reach the signature check, which is what keeps /.env — a file with no fixed magic bytes — from being reported on body size alone.

Seeing It Run

Pointed at a target with a leftover .git directory, a readable .env, and a backup archive sitting in the web root, the scanner confirms each one by signature, reports a blocked admin config as an INFO-level 403, and skips every soft-404 path without printing a single false positive.

Remediation: Closing the Gaps It Finds

Every finding here maps to a config change, not a code review. On Nginx, dotfiles and dot-directories are blocked in one rule:

/etc/nginx/conf.d/block-sensitive.conf Nginx 
# Blocks /.git, /.env, /.htaccess, and any other dotfile or
# dot-directory from ever being served, regardless of app routing.
location ~ /\.(?!well-known) {
    deny all;
    return 404;
}

# Backups and dumps have no reason to be reachable over HTTP at all.
location ~* \.(sql|zip|bak|tar\.gz)$ {
    deny all;
    return 404;
}

On Apache, the equivalent lives in the vhost config or a root-level .htaccess:

.htaccess Apache 
# Deny access to version control, env files, and common backup
# extensions regardless of how deep in the tree they end up.
<FilesMatch "^\.(git|env|htaccess)">
    Require all denied
</FilesMatch>

<FilesMatch "\.(sql|zip|bak)$">
    Require all denied
</FilesMatch>

Two things matter more than the rule syntax itself. First, backups and dumps shouldn't be reachable through the web root in the first place — a cron job that drops dump.sql next to index.html is one misconfigured deploy away from being public no matter how the server is hardened, so the fix is moving the backup destination outside the served directory, not just blocking the request. Second, if config_checker.py (or anyone else) ever does confirm a live .env or database dump, blocking the path after the fact doesn't undo the exposure — every credential in that file needs to be rotated immediately, on the assumption that it was already read before anyone noticed.
