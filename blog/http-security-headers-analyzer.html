HTTP Security Headers Analyzer: Grading a Site's Security Posture From the Command Line

By Artem Kysylov

Before anyone touches a login form or fuzzes an API, real reconnaissance starts somewhere far less glamorous: the response headers a server hands back on a plain GET /. Headers are the server talking about itself — what protections it enforces, what framework rendered the page, sometimes even the exact patch version it's running. Most of that chatter is unintentional, and almost none of it gets reviewed after the initial deploy.

That gap is exactly what HTTP Security Headers Analyzer (header_scanner.py) targets. It's a CLI tool that sends a single request, reads the headers that come back, and turns them into two things an engineer can actually act on: a weighted A–F grade for the site's defensive header posture, and a flagged list of anything the server is leaking about its own stack. Below is a breakdown of how it's built, followed by the real terminal output and some remediation notes for closing the gaps it finds.

Why Header Auditing Is a Recon Fundamental

Response headers do two very different jobs, and most scanners conflate them. The first job is defensive: headers like Content-Security-Policy and Strict-Transport-Security tell the browser how to behave on the user's behalf — refuse to frame this page, refuse to downgrade to HTTP, refuse to sniff a response into executing as a script. Skip one, and you haven't just failed a checklist item; you've left a specific class of attack enabled by default.

The second job is accidental disclosure. A Server: Apache/2.4.41 (Ubuntu) or X-Powered-By: Express header doesn't protect anything — it just tells an attacker which CVE database to open first. Neither problem shows up in a quick glance at the page in a browser. Both show up instantly in curl -I, which is exactly why they're one of the first things a real engagement — or a real attacker — checks before anything else.

"A missing Content-Security-Policy and an exposed Server banner look like the same kind of oversight. They are not the same kind of risk — and a scanner that treats them identically is lying to you with a grade."

Architecture & Code Breakdown

header_scanner.py is built around three cooperating pieces: a weighted scoring table that turns missing headers into a defensible grade, a validation layer that reads header values instead of just checking for presence, and a fingerprinting pass that hunts for anything the server shouldn't be announcing. Here's how each one works.

1. Weighted Security Scoring

Not every missing header is equally dangerous, so the grade isn't a flat count of pass/fail checks. Each header in SECURITY_HEADERS carries its own penalty weight, scaled to how much damage its absence actually enables — a missing CSP costs more than a missing Referrer-Policy because it closes off a far broader class of injection attacks.

header_scanner.py Python 
# Penalty weights reflect real-world exploit impact, not alphabetical
# order — a missing CSP is a far bigger hole than a missing Referrer-Policy.
SECURITY_HEADERS = {
    "Content-Security-Policy":   {"weight": 25, "category": "injection"},
    "Strict-Transport-Security": {"weight": 20, "category": "transport"},
    "X-Frame-Options":           {"weight": 15, "category": "clickjacking"},
    "X-Content-Type-Options":    {"weight": 15, "category": "mime-sniffing"},
    "Permissions-Policy":        {"weight": 15, "category": "feature-abuse"},
    "Referrer-Policy":           {"weight": 10, "category": "leakage"},
}


class AuditReport:
    """Accumulates findings for a single scanned host and converts
    the running score into a letter grade."""

    def __init__(self, host: str):
        self.host = host
        self.findings: list[Finding] = []
        self.score = 100

    def deduct(self, weight: int, reason: str) -> None:
        self.score = max(0, self.score - weight)
        self.findings.append(Finding(weight, reason))

    def grade(self) -> str:
        # A strict curve: anything below a B has at least one
        # high-severity header missing or misconfigured.
        if self.score >= 90:
            return "A"
        if self.score >= 75:
            return "B"
        if self.score >= 60:
            return "C"
        if self.score >= 40:
            return "D"
        return "F"

The grade is a side effect of the running score, never computed from scratch — deduct() is the only thing allowed to touch self.score, which keeps every penalty traceable back to a specific Finding instead of a mystery number.

2. Context-Aware Validation

Presence checks alone produce false positives constantly. The most common one: flagging a missing X-Frame-Options on a site that already blocks framing through Content-Security-Policy's frame-ancestors directive — the modern replacement for XFO. _check_security_headers reads the actual header values before penalizing anything, which also catches headers that are present but neutered, like an HSTS value of max-age=0.

header_scanner.py Python 
def _check_security_headers(headers: dict[str, str], report: AuditReport) -> None:
    csp = headers.get("content-security-policy", "")
    xfo = headers.get("x-frame-options", "").lower()

    # A missing X-Frame-Options isn't automatically a clickjacking hole —
    # CSP's frame-ancestors directive supersedes it and is the modern
    # standard. Flagging both would double-penalize a correctly
    # configured site.
    if not xfo and "frame-ancestors" not in csp:
        report.deduct(15, "No clickjacking protection: missing X-Frame-Options "
                           "and no CSP frame-ancestors directive")
    elif xfo and xfo not in ("deny", "sameorigin"):
        report.deduct(5, f"X-Frame-Options set to unrecognized value '{xfo}'")

    hsts = headers.get("strict-transport-security", "")
    if not hsts:
        report.deduct(20, "Strict-Transport-Security header absent")
    elif "max-age=0" in hsts.replace(" ", ""):
        # Present but neutered — this actively tells browsers to stop
        # enforcing HTTPS, arguably worse than no header at all.
        report.deduct(20, "HSTS max-age=0 disables enforcement entirely")

    nosniff = headers.get("x-content-type-options", "").lower()
    if nosniff != "nosniff":
        # Any value other than the literal string 'nosniff' is ignored
        # by browsers — a typo here silently reopens MIME-sniffing.
        report.deduct(15, "X-Content-Type-Options missing or invalid")

This is the difference between a linter and an auditor. A linter checks that a key exists; an auditor checks whether the value the key holds actually does anything. max-age=0 and a missing header produce the same real-world outcome, so they get the same penalty — but only one of them would be caught by a tool that just checks if header in response.

3. Fingerprinting & Information Disclosure

The second half of the scan has nothing to do with browser enforcement and everything to do with what the server volunteers about itself. Server, X-Powered-By, and X-AspNet-Version are the usual offenders — none of them are required by the HTTP spec, they're just defaults most frameworks ship with and most teams never strip before going to production.

header_scanner.py Python 
# None of these are required by HTTP — they're framework defaults
# most teams forget to strip before shipping to production.
FINGERPRINT_HEADERS = (
    "server", "x-powered-by", "x-aspnet-version", "x-aspnetmvc-version",
)


def _check_leaks(headers: dict[str, str], report: AuditReport) -> None:
    for name in FINGERPRINT_HEADERS:
        value = headers.get(name)
        if not value:
            continue

        # A bare "nginx" is low-risk; a full version string is a
        # targeted CVE lookup away from a working exploit.
        leaks_version = any(char.isdigit() for char in value)
        severity = 5 if leaks_version else 2

        report.deduct(severity, f"'{name}' header discloses: {value!r}")

The version check is deliberately cheap — a single any(char.isdigit() ...) instead of a regex against a CVE database — because the goal here isn't to identify the exact vulnerable build. It's to flag that the server is willing to tell you, so a human (or a follow-up tool further down the Reconnaissance Suite) can go look.

Seeing It Run

In practice the scanner is run against two hosts at once to make the grading curve legible — a hardened target next to one that's shipping defaults. github.com comes back close to a clean sheet on defensive headers; example.com, which exists purely as an IANA placeholder with no hardening applied, comes back with almost every weighted header missing.

Remediation: Closing the Gaps It Finds

Every finding the scanner raises maps to a config change that takes minutes, not a sprint. On Nginx, the defensive headers and the version banner are fixed in the same file:

/etc/nginx/conf.d/security-headers.conf Nginx 
# Defensive headers — matches every entry in SECURITY_HEADERS
add_header Content-Security-Policy "default-src 'self'; frame-ancestors 'none'" always;
add_header Strict-Transport-Security "max-age=63072000; includeSubDomains; preload" always;
add_header X-Frame-Options "DENY" always;
add_header X-Content-Type-Options "nosniff" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;
add_header Permissions-Policy "geolocation=(), microphone=(), camera=()" always;

# Strip the version banner — "nginx" alone leaks far less than
# the default "nginx/1.18.0 (Ubuntu)"
server_tokens off;

Sitting behind Cloudflare adds one more layer worth using: a Transform Rule (under Rules → Transform Rules → Modify Response Header) that removes or rewrites Server and X-Powered-By at the edge, before the response ever reaches the client — useful when you don't control the origin config directly, or want the banner stripped even if a future deploy reintroduces it.
